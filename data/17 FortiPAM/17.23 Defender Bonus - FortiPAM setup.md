How FortiPAM Architecture Works with **FortiGate as a Reverse Gateway**:
* **Contractor → FortiPAM (HTTPS)**: The contractor logs into the FortiPAM portal and requests access to a session.
* **FortiPAM ↔ FortiGate (mTLS control channel)**: FortiGate is registered as the **reverse gateway**, maintaining a certificate-based, trusted connection to FortiPAM.
* **FortiGate → Engineering Device (session traffic)**: When the contractor clicks "Launch," FortiPAM authorizes the request and instructs **FortiGate to proxy the session** (RDP/SSH/etc.) to the engineering device in the OT environment.
* Audit: FortiPAM logs and records the session centrally for auditing purposes.

In one sentence: The contractor interacts with FortiPAM (portal + policy), which communicates with FortiGate (mTLS control channel), and then FortiGate proxies the session traffic to the engineering device.

Current Configuration:
* FortiPAM **Reverse Service**: On FortiPAM, enabling the Reverse Service turns it into a **listener** for the **gateway control channel**.

Diagram: FortiPAM Reverse Service

![FortiPAM diagram](/images/PAM_Flow.png)

1. **FortiGate Reverse Service Configuration**:
	*  You create a **reverse-connector** on the **FortiGate** that points to the FortiPAM Reverse Service IP and port (typically :8443).
	* The **reverse-connector** is bound to the **client certificate** presented by the FortiGate and the trusted CA certificate used to verify FortiPAM’s server certificate (establishing mutual TLS).
	* After enabling the reverse service, the **FortiGate establishes and maintains an outbound control connection** to FortiPAM. This connection allows FortiPAM to instruct the FortiGate to set up user sessions to internal targets.
2. FortiGate Session Traffic Configuration:
	* In this step, you configure the **FortiGate to proxy the actual session** traffic (e.g., RDP/SSH) after the mTLS control channel is established.
	* You enable the **FortiGate's default reverse-mode** VIP/access-proxy/policy, allowing **FortiPAM** to **send** the **launched session** to FortiGate, which then forwards it to the internal target.
3. FortiPAM Secret Gateway Configuration:
	* In FortiPAM, you create a **Secret Gateway** entry with the type set to **Reverse** and specify the **FortiGate’s VIP/port** (the reverse-mode proxy endpoint).
	* When a user clicks **Launch** on a **secret**, FortiPAM knows which **FortiGate gateway** to **forward** the **session** to.

This setup ensures seamless **proxying** of **session traffic** from the **contractor** to the **internal engineering** device through **FortiPAM** and **FortiGate**.

### Certificate Roles (Who uses what?)

There are two sides in the mTLS connection:

1. 	**FortiPAM** (Server side)
	* Presents a server certificate
	* This proves: “I am the real FortiPAM”

2. **FortiGate** (Client side)
	* Presents a client certificate
	* This proves: “I am a trusted FortiGate gateway”

Because it’s **mutual TLS** (mTLS), **both sides authenticate** each other.

<div class=info>
	
Whenever you upload a certificate in your FortiGate firewall, it gets a name assigned automatically. Sometimes this is not what you want, so for that it's easier to **rename** the **certificate** for clarity.
	
Go to the certificate settings:

Local certificates: 
```
config vpn certificate local
```

CA certificates: 

```
config vpn certificate ca
```

Remote certificates: 
	
```
config vpn certificate remote
```

To rename a certificate, use:

```
rename old_name to new_name
```
